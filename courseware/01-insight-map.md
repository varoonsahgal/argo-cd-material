# Neural Networks and Deep Learning: Canonical Insight Map

**Status:** Curated production input for Student Guides, labs, challenges, instructor guides, and slides  
**Authority:** `neural-networks-outline.md` remains the authoritative scope; `courseware/00-course-blueprint.md` remains the canonical ID, timing, path, and scope contract.  
**Use rule:** These are recommendations, not a requirement to use every idea. Producers should select the few ideas that make each timed block cohere. Do not add time, rename IDs, promote `OPTIONAL`/`MOVE` material into the live core, or turn the course into an LLM course.

## How to Use This Map

- Put the intuitive explanation and prediction before notation, code, or the revealing visual.
- Make each visual expose one relationship. Ask what learners notice before explaining it.
- Keep participant artifacts answer-free. Expected diagnoses, reveal sequencing, and acceptable alternatives belong in instructor-only artifacts.
- Preserve the canonical loop: **Explain -> Visualize -> Predict -> Experiment -> Observe -> Diagnose -> Explain Why**.
- Treat a model result as evidence, not as a verdict. Ask what else could have produced it and what observation would discriminate among explanations.
- Use current-practice connections as short transfer bridges. Their purpose is to show that the fundamentals recur in larger systems, not to imply mastery of frontier-model implementation.
- Recheck every item in [Claims Requiring Current Primary-Source Verification](#claims-requiring-current-primary-source-verification) during production. A dated verification snapshot is not a promise about future releases.

## Cross-Course Memory Spine

| Day | Memorable line | Learner disposition it should create | Accuracy limit |
|---|---|---|---|
| Day 1: See It | **A neural network is a chain of adjustable transformations; a prediction is the trace those settings produce.** | Inspect the transformation before calling the behavior intelligent. | This describes feedforward mechanics, not every architecture or source of model behavior. |
| Day 2: Train It | **Forward propagation makes the prediction; backpropagation carries sensitivity backward; the optimizer turns that sensitivity into a parameter change.** | Trace responsibility before changing training code. | A gradient is local sensitivity, not causal blame or a guarantee that an update improves every metric. |
| Day 3: Scale It | **A stronger architecture cannot rescue invalid evidence.** | Audit data provenance and generalization before celebrating capacity. | Valid data handling is necessary, not sufficient, for a useful model. |
| Day 4: Decide It | **The best next experiment is the one that most clearly separates plausible explanations.** | Optimize for information gained, not knobs tried. | Real interventions can interact; the one-change rule is a teaching and diagnosis discipline, not a universal experimental design. |

## Visual and Challenge Grammar

| Surface | Default visual | Required learner action | Do not imply |
|---|---|---|---|
| Boundary motion | Animated contour plus fixed probe points | Predict rotation, translation, and confidence change separately | That a 2D line fully represents high-dimensional model behavior |
| Hidden transformation | Raw-space and hidden-space plots with the same point identities/colors | Trace which points become easier to separate | That hidden units always correspond to named human concepts |
| Gradient flow | Forward values and backward sensitivities on the same tiny graph | Predict sign before magnitude; verify numerically | That gradient color/size is causal attribution or global importance |
| Batching and shapes | Tensor tiles with labeled dimensions and the same operation at batch sizes 1, 32, 1,024 | State every dimension before execution | That larger batches are always faster or always better for learning |
| Leakage provenance | Data lineage with timestamps, split boundary, and fitted-statistic arrows | Mark where validation knowledge crosses into training | That high scores alone prove leakage or that removing one leak proves validity |
| Feature maps | Input, selected channels, receptive-field cue, and later maps | Compare spatial detail and selectivity | That a bright activation is a complete explanation of a prediction |
| Learning curves | Aligned train/validation curves with intervention marker | Name evidence, competing diagnosis, and disconfirming observation | That one curve shape uniquely identifies one root cause |
| Thresholds | Probability strip, moving threshold, confusion counts, cost curve | Choose an operating point from consequences | That the model itself chooses the socially or operationally correct cost |
| Error slices | Aggregate metric -> confusion pair -> slice -> examples | Quantify prevalence and consequence before proposing a fix | That manually chosen slices are exhaustive, independent, or causal |
| Quality/resources | Pareto scatter or table for quality, latency, throughput, size, memory | Choose for a stated constraint and identify dominated options | That one model is universally best or that classroom timing equals production cost |

# Day 1: See It

**Canonical question:** How can simple mathematical operations produce intelligent-looking behavior?  
**Signature arc:** Make one parameter visible -> let a linear model succeed -> expose its limit -> transform the representation -> trace the complete forward path.  
**Day one-liner:** **A boundary is where weighted evidence and bias exactly cancel.**

## Day 1 Lab Signature Moments

### `LAB-D1-01` - One-Neuron Boundary Workshop

- **Insight:** Parameter meaning becomes memorable when learners can predict motion, move one control, and reconcile the result with $w\cdot x+b=0$.
- **Why / best moment:** Use the two stubborn points after the first mostly-correct setting. They make "accuracy went up" less informative than "which boundary property changed?"
- **Predict before run:** For each isolated change to `w1`, `w2`, and `b`, sketch whether the `0.5` contour rotates, translates, or stays fixed while probability shading changes. Commit on paper before touching sliders.
- **Notebook visual contract:** Keep probe identities fixed; overlay old/new contours and a difference strip for probe probabilities. Learners must observe that scaling both weights and bias can leave the class boundary unchanged while sharpening sigmoid confidence. Do not imply sharper confidence is better calibration.
- **Break/fix and counterintuitive reveal:** Offer a "change all parameters" attempt that may improve accuracy but destroys attribution. Reset, change one variable, and recover a causal explanation.
- **Explain-why debrief:** "Which observation distinguishes location change from confidence change? What remained invariant? Why would manual search collapse as parameter count grows?"
- **Misconception correction:** If learners say bias rotates the line, set two bias values and calculate two points on each contour; compare slopes directly.
- **Engineering bridge / source:** This is the seed of controlled parameter experiments and regression probes. Mathematical/experimental-design content; no current source check required.

### `LAB-D1-02` - The Linear Limit

- **Insight:** Let a simple model succeed before it fails; the hidden transform is then a response to evidence, not decorative complexity.
- **Why / best moment:** Hide the XOR accuracy while showing the learned region first. Ask whether more epochs could change the *kind* of boundary.
- **Predict before run:** Rank expected performance on blobs, XOR, fixed nonlinear hidden features, and the same hidden stack with identity activations.
- **Notebook visual contract:** Use linked raw-space/hidden-space plots with identical point colors and thin connector lines for four anchor examples. Learners must observe that nonlinear hidden coordinates make a linear output sufficient. Do not imply every hidden coordinate has a stable semantic label.
- **Model-detective reveal:** Reveal boundary, then accuracy, then implementation. This ordering tests mechanism diagnosis rather than code spotting.
- **Counterintuitive result:** More linear layers still cannot solve XOR; a small fixed nonlinear network can outperform a trained one-neuron classifier without any participant-side neural-network training.
- **Explain-why debrief:** "Did the output boundary become nonlinear, or did the representation make a simple boundary useful? What evidence separates those descriptions?"
- **Engineering bridge / source:** Distinguish feature engineering/representation learning from optimizer problems. Stable conceptual content; no current source check required.

### `LAB-D1-03` - Shape and Activation Observatory

- **Insight:** Shapes are executable hypotheses; activation pathologies should be seen in values, not memorized as vocabulary.
- **Why / best moment:** Make every TODO begin with an expected shape/range field. The wrong-axis softmax should fail a learner-written invariant rather than an instructor warning.
- **Predict before run:** State output shape and row-sum behavior for correct and wrong-axis softmax; predict which extreme inputs create sigmoid saturation or dead ReLU output.
- **Notebook visual contract:** Pair activation curves with a heatmap of actual pre- and post-activation values. Learners must observe where slope/information is compressed or zeroed. Do not imply zero activation always means a permanently dead unit.
- **Break/fix:** Wrong-axis softmax yields valid-looking numbers but fails per-example row sums. Strongly negative ReLU input produces all-zero outputs; learners alter input distribution or activation and explain the change.
- **Explain-why debrief:** "Why can code run with the wrong axis? Which invariant catches it? Why is shape correctness necessary but not semantic correctness?"
- **Misconception correction:** If learners treat softmax as independent sigmoids, change one logit and observe every class probability move because of shared normalization.
- **Engineering bridge / source:** Shape assertions and semantic invariants recur in data pipelines and distributed systems. NumPy implementation is stable; framework-specific equivalents require production verification.

### `LAB-D1-04` - Build a Network That Thinks Forward

- **Insight:** A model can be mostly right for a traceable reason and wrong for a traceable reason; neither outcome requires anthropomorphic explanation.
- **Why / best moment:** Keep the two mystery failures unnamed until learners commit from raw geometry, then reveal probability, boundary, and hidden representation in stages.
- **Predict before run:** Select two likely failures and name the evidence expected in raw space and hidden space if the prediction is correct.
- **Notebook visual contract:** Use a four-panel evidence board: raw data/probes, decision region, hidden representation, and six-row trace table. Learners must observe disagreement between geometric intuition and learned boundary near noise/overlap. Do not imply a 2D hidden projection preserves every relationship in six dimensions.
- **Break/fix:** Present a transpose error first as shape evidence, then let learners repair it. Later perturb a copied parameter and require one predicted local consequence before plotting.
- **Explain-why debrief:** "For each wrong probe, which intermediate evidence changed your initial story? What can this trace explain, and what would require training evidence?"
- **Misconception correction:** Replace "the network knows" with a parameter-and-activation statement; require the learner to cite a row, contour, or hidden coordinate.
- **Engineering bridge / source:** Connect the evidence board to behavior analysis and regression cases while caveating that activation inspection is not complete interpretability. Any current tooling examples are `VERIFY-CURRENT` (`SRC-15`).

# Day 2: Train It

**Canonical question:** When a neural network makes a mistake, how does it know what to change?  
**Signature arc:** Give error a scalar form -> reveal slope -> carry local sensitivities backward -> batch the work -> build it -> reveal framework automation -> diagnose failures.  
**Day one-liner:** **Loss is the signal the optimizer can act on; a metric is evidence humans use to judge whether the result matters.**

## Day 2 Lab Signature Moments

### `LAB-D2-01` - Loss Landscapes and Learning-Rate Roulette

- **Insight:** Learning rate is a multiplier on local sensitivity; its behavior is visible as motion, not merely a hyperparameter label.
- **Why / best moment:** Keep the fixed update budget. It makes "too small" visible as insufficient progress rather than mathematically wrong.
- **Predict before run:** Rank BCE cases, then classify four hidden trajectories as crawl, smooth convergence, oscillatory convergence, or divergence and sketch the first three steps.
- **Notebook visual contract:** Align parameter position, loss-over-step, and distance-to-optimum plots. Learners must observe that `0.90` can cross the minimum repeatedly yet converge, while `1.10` grows. Do not generalize these numeric thresholds beyond the chosen quadratic.
- **Counterintuitive reveal / break-fix:** Equal class accuracy can hide sharply different loss; oscillation is not automatically divergence; unclipped hand-written BCE can produce non-finite values.
- **Explain-why debrief:** "Which trajectory label could you infer from only the last loss, and which requires the path? How does update sign explain the alternating sides?"
- **Engineering bridge / source:** Connect to learning-rate diagnostics and stable objective implementation. Framework loss details are `VERIFY-CURRENT` (`SRC-02`); the quadratic result is local to the lab.

### `LAB-D2-02` - Backpropagation and Gradient Check

- **Insight:** Gradient checking turns an invisible backward pass into a falsifiable claim.
- **Why / best moment:** Ask for signs before exact values. A wrong sign is conceptually diagnostic even when arithmetic is incomplete.
- **Predict before run:** For selected weights/biases, predict whether a small increase raises or lowers loss and identify the path that supports the prediction.
- **Notebook visual contract:** Computational graph plus analytic/numerical table with signed values and relative error. Learners must observe that a missing local derivative creates a structured mismatch, not random noise. Do not imply finite differences are the normal training algorithm.
- **Model detective / break-fix:** Reveal only the relative-error pattern for the sign bug and missing-sigmoid-factor bug; learners name the likely local defect before opening the faulty function.
- **Explain-why debrief:** "Why does one small parameter perturbation test the whole chain? When could finite differences become misleading?"
- **Misconception correction:** If learners say numerical agreement proves the model is useful, separate derivative correctness from objective/data validity.
- **Engineering bridge / source:** Connect to unit-testing custom differentiable code. NumPy gradient check is stable; any framework grad-check API would require current verification.

### `LAB-D2-03` - Train a Neural Network with NumPy

- **Insight:** The training loop should emit evidence at every stage, not only a final score.
- **Why / best moment:** Make the initial loss prediction and stage invariants the lab's spine; plotting is evidence collection, not decoration.
- **Predict before run:** Predict initial BCE band, the direction of early loss change, and the boundary family for nonlinear versus no-activation variants.
- **Notebook visual contract:** Dashboard with aligned train/validation loss, accuracy, decision boundary snapshots, and gradient-norm strip. Learners must observe whether optimization changes the boundary while generalization remains plausible. Do not imply monotonic mini-batch loss or exact reproducibility.
- **Break/fix:** Select too-high learning rate or no activation. Require symptom, discriminating check, repair, and before/after overlay; NaNs stop with a bounded diagnostic rather than scrolling onward.
- **Counterintuitive result:** A model can show decreasing loss yet retain a linear representational limit; wider is not automatically better under the same data/budget.
- **Explain-why debrief:** "Which evidence supports optimization progress, which supports representational adequacy, and which supports generalization?"
- **Engineering bridge / source:** This becomes the reference trace for PyTorch and later regression investigations. Stable NumPy mechanics; no current framework claim.

### `LAB-D2-04` - PyTorch Autograd: Break It and Fix It

- **Insight:** Framework debugging is strongest when learners diagnose evidence before seeing faulty source.
- **Why / best moment:** Present one mystery card per team. Let teams request one evidence reveal at a time: curve, gradient norms, activation summary, mode state, then code.
- **Predict before run:** Map every framework call to a NumPy responsibility and predict the baseline range before training.
- **Notebook visual contract:** Before/after evidence board with identical axes and a call-to-mechanic trace. Learners must observe distinct signatures for missing nonlinearity, accumulated gradients, output/loss mismatch, and mode misuse. Do not imply each signature is unique.
- **Break/fix:** Require a written diagnosis and cheapest check before code access. The fix must restore the invariant and the learner must explain why, not merely rerun.
- **Counterintuitive reveal:** `model.eval()` changes behavior of selected modules but is not itself a gradient-disabling context; zeroing to `None` may alter gradient inspection behavior in current PyTorch. Both details must be version-checked.
- **Explain-why debrief:** "What did the framework automate? What judgment remained yours? Which evidence would catch this defect in a larger run?"
- **Engineering bridge / source:** Connect to training regression detection and reproducible failure reports. All exact PyTorch syntax/semantics are `VERIFY-CURRENT` (`SRC-01` to `SRC-05`).

## Day 3 Lab Signature Moments

### `LAB-D3-01` - Find the Data Leak

- **Insight:** A lower honest score is more valuable than a near-perfect invalid score.
- **Why / best moment:** Start with the suspicious report, not the code. Let learners decide what would make the result implausible and what evidence they want.
- **Predict before run:** Rank likely explanations for near-perfect validation: true signal, duplicate contamination, post-outcome feature, split/preprocessing leak, evaluation bug. Name a discriminating check for the top two.

- **Counterintuitive result:** Performance drops after the pipeline is improved; the course should label this a validity gain, not a model regression.
- **Explain-why debrief:** "Which information crossed the split boundary? Why is training-only fitting different from applying the same transform to validation? What validity risk remains?"

### `LAB-D3-03` - Make It Overfit, Then Rescue It

## Production Selection Test

Before carrying an idea into a downstream artifact, ask:

1. Does it reinforce the objective attached to the canonical ID?
2. Can it fit inside the existing timed block by replacing exposition rather than adding scope?
3. Does the learner commit to a prediction, diagnosis, or choice before the reveal?
4. Is the observable evidence clear, and does the debrief ask what happened, why, and what transfers?
5. Does the visual state what to observe and what not to infer?
6. Is the misconception correction an action or evidence check rather than a warning sentence?
7. Is any current API/practice claim linked to a verification row and a dated primary source?
8. Does participant-facing material remain free of completed answers, hidden diagnoses, and instructor-only notes?

Select fewer, stronger ideas when time is tight. Preserve prediction and debrief time before optional detail.
