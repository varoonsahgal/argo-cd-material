# Shared Lab Environment

This guide covers the participant notebooks through Day 4. Package installation may require network access; the Day 1 and Day 2 labs generate their data in memory. Day 3 defaults to course-supplied offline artifacts and makes torchvision downloads explicit and opt-in. Day 4 uses generated data or packaged fixed digits evidence and requires no network. No notebook depends on another notebook's kernel state.

## CPU Baseline

- CPU is the required path for Days 1-4. No participant needs a GPU, Apple MPS device, or other accelerator.
- All Day 1 and Day 2 datasets are generated in memory. No dataset download is required.
- Day 1 completed notebooks are expected to run in under 20 seconds of compute, excluding participant work and discussion.
- Day 2 targets are under 10 seconds for `LAB-D2-01` and `LAB-D2-02`, under 60 seconds for the `LAB-D2-03` baseline, and under 6 minutes for the complete `LAB-D2-04` break/fix path.
- Day 3 targets are under 30 seconds for `LAB-D3-01`, under 12 minutes for `LAB-D3-02`, under 10 minutes for the baseline plus one intervention in `LAB-D3-03`, and under 15 minutes total for `LAB-D3-04`. A first canonical MobileNet CPU extraction targets under 12 minutes; a cache hit targets under 2 minutes.
- Day 4 targets are under 30 seconds for `LAB-D4-01` and the `LAB-D4-02` core, under 8 minutes for `LAB-D4-03` including fresh reruns, and under 12 minutes for one complete capstone profile. The validated local completed paths were substantially faster on the recorded Apple-silicon CPU; those timings are not universal promises.
- A practical minimum is 2 CPU cores and 4 GB of available memory for the PyTorch path. Day 1 and the NumPy-only Day 2 labs need substantially less.

Accelerator availability is informational. Do not change a required lab's device, seeds, run budget, or evidence bands when performing the course path.

```bash
python -m pip install torch==2.6.0 torchvision==0.21.0

If that command does not provide a CPU-compatible wheel for the host, use the **CPU** option in PyTorch's official [Start Locally selector](https://pytorch.org/get-started/locally/), then record the installed version and run the checks below.

## Day 3 Offline Data and Cache Contract

Repository-supported artifacts live under `courseware/shared/data/day-3/`. `manifest.json` is the machine-readable source of truth for byte sizes, SHA-256 checksums, generation environment, source/license notes, and claim boundaries.

| Artifact | Purpose | Packaged count/shape | SHA-256 |
|---|---|---|---|
| `fashion_mnist_fallback.npz` | Real Fashion-MNIST recovery data for `LAB-D3-02` and `LAB-D3-03` | `3,000/800/800`, uint8 `28x28` images | `c3fd6c0581b5baf626dfd59e735ac6f787a858a488db4afd09d2e0cbd4294122` |
| `transfer_surrogate_fashion_subset.npz` | Fixed recovery images for the transfer-race scratch side | `2,400/800/800`, uint8 `28x28` images | `605aa62f6b4260203c6d205dac3fac432c434818e77316cc2f254ee84e85c9db` |
| `transfer_surrogate_embeddings.npz` | Label-blind recovery features for new-head training | `(2400,256)/(800,256)/(800,256)`, float16 | `39fd63a657d0a2ecdc2e88c4a512aaea9f55e5af86c424908e7d5250934e6c5a` |

The Fashion-MNIST artifacts come from the official Fashion-MNIST train/test files distributed through torchvision; the upstream Fashion-MNIST repository states the MIT license. The transfer recovery features are generated without labels by 4x4 mean/gradient pooling followed by a seeded random projection and `tanh`. They are **not** CIFAR-10 or MobileNet features. No trained classifier head, predictions, checkpoint, completed learner model, or response key is packaged.

The recovery path preserves image/label loading, batch/channel shapes, bounded scratch training, temporary feature-map hooks, tiny-data overfitting, one-remedy comparison, feature-cache loading, new-head training, freeze reasoning, and scoreboard construction. It does not validate the full Fashion-MNIST metric band, CIFAR-10 behavior, MobileNet pretrained extraction, canonical extraction time, wrong-normalization metric degradation, or a transfer advantage.

### Default offline use

Keep each notebook's `ALLOW_DOWNLOAD = False`. Run from a repository checkout so the notebook can find `courseware/shared/data/day-3/manifest.json`. `LAB-D3-02` and `LAB-D3-03` use the packaged Fashion-MNIST fallback when a complete torchvision cache is absent. `LAB-D3-04` uses the explicitly labeled recovery images/features when canonical CIFAR-10 or pretrained weights are unavailable.

`LAB-D3-04` checks the exact `MobileNet_V3_Small_Weights.DEFAULT` Torch Hub cache file before attempting CIFAR-10. With downloads disabled, a missing weight file selects recovery before any CIFAR constructor or network request, even when CIFAR-10 is already cached.

### Opt-in cache and download use

Set `ALLOW_DOWNLOAD = True` only when network use is intentional. Torchvision source files are cached below `.cache/day-3/torchvision/`; canonical transfer embeddings are cached below `.cache/day-3/` with a key that includes weight identity, `repr(weights.transforms())`, the image/label split fingerprint, and torchvision version.

For `LAB-D3-04`, opt-in mode preflights and caches the selected weight state before opening CIFAR-10. A failed weight fetch selects the labeled recovery path before scratch training starts, so the scoreboard cannot mix a CIFAR scratch result with surrogate features.

The canonical transfer code uses:

```python
weights = MobileNet_V3_Small_Weights.DEFAULT
transform = weights.transforms()
model = mobilenet_v3_small(weights=weights)
```

The stable weight-enum API was source-checked for production. The exact `DEFAULT` alias, bundled transform details, files, and metric bands remain version-qualified and must be rechecked when torchvision changes. A complete canonical CIFAR-10/weight download did not finish during local production, so the online path remains structurally checked but not execution-validated.

## Restart and Run All Contract

Every notebook must work independently. It must not rely on variables, imports, files, outputs, or kernel state from another lab.

Before a validation run:

1. Select the intended kernel or Colab runtime.
2. Restart the kernel/runtime and clear all outputs.
3. Run cells in order from the top.
4. Stop at an intentional learner prediction gate or `TODO` only when the notebook directs you to complete it.
5. Complete the learner path without changing supplied seeds, datasets, fixed parameters, run budgets, or evidence bands.
6. Restart again and use **Run All** from the top.
7. Confirm every required checkpoint and deliberate failure/recovery path under that clean state.

Changing a seed, running cells out of order, or retaining a variant's state can invalidate the documented sanity bands.

## Troubleshooting

| Symptom | Likely cause | Recovery |
|---|---|---|
| `ModuleNotFoundError` | The selected kernel is outside the environment where packages were installed. | Select the named kernel, restart, and rerun the import check. |
| `ModuleNotFoundError: torch` | PyTorch is absent from the selected Day 2 kernel. | Install a CPU-compatible PyTorch build, select the same kernel, restart, and rerun the checks. |
| A newly installed version is not visible | The notebook kernel/runtime was not restarted. | Restart and run from the top. |
| Plots do not appear | The plotting cell was skipped or the backend is stale. | Restart, run imports first, and execute in order. |
| Results differ from a sanity band | Seed, data, fixed parameters, device, or an explicit default changed. | Restore the supplied setup and rerun from a clean CPU kernel. |
| A shape error mentions matrix multiplication or loss targets | A learner `TODO` returned the wrong orientation or a deliberate variant is active. | Print each array/tensor shape and compare it with the notebook's shape contract. |
| Optional device reports `cpu` | No supported accelerator is available to this runtime. | Continue on CPU; this is the required and validated path. |
| Day 3 reports a packaged fallback | Dataset or weight cache is absent and downloads are disabled/unavailable. | Continue with the labeled recovery path, or intentionally set `ALLOW_DOWNLOAD=True` before class. |
| Day 3 support file is missing | The notebook was copied without the repository support directory. | Run from the checkout or upload `courseware/shared/data/day-3/` beside the course tree. |
| Day 4 manifest or `.npz` file is missing | The notebook was uploaded without the complete repository-relative Day 4 support tree. | Upload or clone `courseware/shared/data/day-4/`, keep its path relative to the notebook/course tree, verify all ten `.npz` files against `manifest.json`, and restart from the top. |
| CIFAR-10 download was interrupted | Network throughput or classroom access is unreliable. | Return to `ALLOW_DOWNLOAD=False`; do not present a partial download as canonical validation. |
| Transfer cache is stale | Weights, transforms, split, or torchvision changed. | Delete only the affected keyed cache and regenerate; never reuse it under a different key. |
