# THREE THINGS THIS COURSE MUST DELIVER

1. **Detailed challenge exercises that double as student guides.** Every outline session becomes one Markdown file that explains the concept in extreme, assume-nothing detail — beginner-clear, with grounded vocabulary, analogies, and amazing, memorable key takeaways — and, where the outline pairs it with a Lab, gives participants a real, guided hands-on exercise in that same file. Initial labs (Day 1, Labs 1-2) must be the most heavily guided, detailed, and insightful; later labs progressively ask for more independent thinking, and the capstone is deliberately diagnostic.
2. **Screenshots, everywhere the UI matters.** Every step that tells a participant to open, click, or observe something in the Argo CD UI needs a real, version-accurate screenshot, or a precise capture-spec placeholder if one truly cannot be sourced yet. Use the web to capture these from the course's own live environment when possible, or from current official Argo CD documentation with attribution otherwise — and use the web to confirm every version-specific claim (CLI flags, UI layout, install commands, current best practice) before it lands in a guide.
3. **Extreme setup detail.** Terraform-provisioned infrastructure, one virtual machine per student, each running the two-cluster (management + workload) Kubernetes topology with Argo CD preinstalled — plus extremely detailed, beginner-clear instructor and student setup guides. Terraform is written and locally validated, but real cloud infrastructure is only ever applied/destroyed by the instructor's own explicit action, never automatically.

# HANDS-ON WORK IS A MAJOR PRIORITY, NOT DECORATION

This is a **hands-on, exercise-heavy operations course**, not a lecture course with a few exercises attached. Build exactly the sessions, labs, and capstone the outline specifies — do not inflate or deflate the lab count — but make every session non-passive:

- Concept-guide sessions (no dedicated Lab) still include 2-4 Quick Checks and one short, optional Try-It-Yourself micro-task.
- Lab/Capstone sessions are full challenge exercises: guided walkthroughs, exercises ordered easiest to hardest, troubleshooting, and a self-checkable checkpoint.

Guides must be **detailed enough that someone can work through them without guessing**. Where relevant, include:

- Clear purpose and learning objectives
- Expected duration
- Environment and prerequisite checks (grounded in the real environment Environment Engineer builds)
- Exact commands and exact UI navigation, screenshotted
- Explanation of what each major step is doing and why
- Prediction questions before an important sync, deploy, or diagnostic reveal
- Expected CLI output, sync/health status, and sanity checks — real, verified output, not invented
- Deliberately broken examples and troubleshooting tasks
- Common mistakes and recovery guidance
- Exercises that require decisions and diagnosis, not just copying
- Optional stretch challenges, clearly marked
- Key takeaways
- No completed answers in participant guides; every lab guide has a separate, executed, and validated solution file

The preferred learning loop is:

**Observe -> Predict -> Change -> Sync/Apply -> Inspect -> Diagnose -> Explain -> Extend**

Avoid guides whose primary activity is copying completed commands and running them.

# MAKE THE LABS INTERESTING

Actively incorporate patterns such as (see the `challenge-designer` skill for the full set):

- **Predict Before You Sync** — commit to an expected result before syncing or applying a change
- **Break It / Fix It** — a deliberately broken values file, revision, or credential that must be diagnosed and repaired through Git
- **Root-Cause Detective** — diagnose a problem from Argo CD/Kubernetes evidence alone, without seeing the underlying change
- **Guardrail Bypass Attempt** — try an action an AppProject/RBAC boundary should block, confirm it's blocked, explain why
- **Pattern Showdown** — implement the same requirement with ApplicationSet vs. App-of-Apps and compare operational impact
- **You Get One Diagnostic Action** — under a multi-fault scenario, choose the single highest-information next step before changing anything
- **Restore the Platform** — the capstone: a multi-layer failure participants must diagnose and repair using evidence, then explain the guardrail that would prevent recurrence

Use comparison and competition carefully: reward reasoning, diagnosis, and explanation — never merely speed.

# ORCHESTRATION WORKFLOW

## 1. Course Architect
Invoke first. Ask it to analyze the outline, create `courseware/00-course-blueprint.md`, assign each session to a concept guide or lab guide, validate timing, map objectives to evidence, define the environment specification, and define the screenshot plan and file tree. Do not proceed until the blueprint is coherent.

## 2. Insight Generator
Invoke after the blueprint exists. Ask it to create `courseware/01-insight-map.md`: sticky explanations, visual revelations, counterintuitive results, engineering trade-offs, failure stories, current platform-engineering connections, and memorable key takeaways — with a verification note on any current-practice claim.

## 3. Environment Engineer
Invoke after the blueprint's environment spec exists, and before Lab Engineer starts writing. Ask it to build the Terraform (parameterized by student count), the bootstrap/reset/capstone-fault-injection scripts, and the instructor and student setup guides — and to locally validate all of it (`fmt`/`validate`/`plan`, `shellcheck`, a local `kind`/`k3d` smoke test where possible). Confirm it did not apply or destroy any real infrastructure.

## 4. Lab Engineer
For every planned file, invoke Lab Engineer with the outline section(s), blueprint section, insight-map entries, the environment specification's concrete details (exact commands/cluster names/URLs), and the target path. It must produce one Markdown file per session — concept guide or lab guide as assigned — following the beginner-clarity mandate, the progressive-scaffolding rule, and the screenshot requirement.

## 5. Lab Tester — EXECUTION IS REQUIRED
After each lab guide is created, invoke Lab Tester. It must **actually execute the guide** against a real or local-sandbox environment, not just inspect it: run every command, reach every checkpoint, verify every screenshot against the real UI encountered, and confirm deliberate failures and their fixes work. Statuses: **PASS**, **PASS WITH NOTES**, **FAIL** (loops back to Lab Engineer and is retested), or **NOT EXECUTABLE** (documented external limitation). Do not let Course Reviewer substitute for this execution step.

## 6. Lab Solution Engineer — SEPARATE SOLUTIONS + EXECUTION
After a lab guide passes Lab Tester, invoke Lab Solution Engineer. It creates the separate solution file under `courseware/solutions/`, mirroring the guide's name with a `-SOLUTION.md` suffix, answering every exercise with reasoning and expected results — then **executes it end-to-end** and verifies no answers leaked into the participant guide. A required lab is not complete until **Lab Guide PASS + Solution PASS**. If the solution exposes a flaw in the guide, route back through Lab Engineer and Lab Tester before reconciling the solution.

## 7. Pedagogy Reviewer
After each day is built and its labs validated, invoke Pedagogy Reviewer against `standards/pedagogy-rubric.md`. Require actionable findings using: **KEEP / CUT / SHORTEN / MOVE / ADD ACTIVITY / ADD VISUAL / ADD PRACTICE / CLARIFY**. Apply worthwhile changes rather than merely storing the report.

## 8. Course Reviewer
After both days are built, tested, reviewed, and revised, invoke Course Reviewer against `standards/quality-rubric.md` to review the complete `courseware/` tree — including `environment/` and `assets/` — for scope alignment, technical accuracy and currency, lab integrity, environment readiness, visual/screenshot completeness, cross-day consistency, and delivery readiness. Write `courseware/99-final-quality-report.md`.

If blocking/high-severity issues remain, invoke the appropriate agent, fix them, and rerun the required review/test.

# MODERN PLATFORM-ENGINEERING CONNECTIONS

Throughout the course, connect fundamentals to problems a platform/DevOps engineer runs into in current practice: progressive delivery, policy-as-code guardrails, multi-cluster fleet management, internal developer platforms, incident response, and — briefly, only where the outline calls for it — how Argo CD relates to Argo Workflows. Keep these grounded and understandable; do not turn the course into a broader GitOps-tooling survey.

# QUALITY BAR

Every guide should help answer:

- What is this, in plain language?
- Why does it matter operationally?
- Can I see it (a diagram or a real screenshot)?
- Can I predict what will happen before I act?
- Can I try it myself?
- What can go wrong, and how would I know?
- Can I diagnose the problem from evidence alone?
- What should I remember tomorrow?

Favor: **Show it -> Predict it -> Try it -> Break it -> Fix it -> Explain it**
